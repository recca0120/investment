# 網站設計：流程與規則

使用者是股市新手、也不懂設計。網站的目的是**讓新手讀得懂、讀得下去**，所以每個設計決定都要能回答：「這樣新手讀起來有比較容易嗎？」

這份 skill 收的是使用者在對話中提過的要求，以及已經做出的設計決定。規則後面都寫了原因，碰到沒寫到的情況，依原因判斷。

## 使用者對「怎麼做設計」的要求

這些是使用者明確講過、而且我曾經做錯被糾正的：

1. **不要拿設計問題問使用者。** 寬度、分頁形式、首頁放什麼、選 A／B／C，使用者都回答過「我不懂設計」「我也不知道哪個好，你先幫我決定」。要做的是：上網研究人怎麼閱讀比較舒服 → 自己決定 → 做樣稿給使用者看。只有真正屬於使用者的事才問（內容要放什麼、想要的感覺、取捨的後果）。
2. **方向不確定時，做 2～3 份 HTML 樣稿讓使用者看圖挑。** 樣稿用同一份真實內容，差別要大到一眼看得出來；附上各自的優缺點和我的建議。小改動（例如一個彈出卡片）做一份實驗版截圖就好，不用三份。
3. **整體畫面要仔細設計，不交框架預設外觀。** 該用分頁就用分頁、該用圖解就用圖解；美感方向用 `frontend-design` skill。
4. **能用現成元件就用，要和 Tailwind 相容。** 本 repo 用 daisyUI（使用者問過「為什麼不用 daisyui？」）。daisyUI 沒有、或 Starlight 已有做好無障礙的元件（例如文章分頁 `<Tabs>`），才另外處理。
5. **程式化設計：顏色、字體、圓角只有一個來源。** 使用者說「應該先定義一個 theme 的檔案，然後用編譯的方式，css 才不會四處散亂」。改 `site/design/tokens.ts`，不在元件或 CSS 寫死顏色（有測試擋）。
6. **自己驗證，不要叫使用者回報。** 交出去之前自己截圖看過：電腦日間、夜間、手機。使用者說過「你不是用 ATDD 為什麼還要我回報？」。樣稿、比較頁也一樣：用瀏覽器打開確認圖片有出來、沒有 JS 錯誤，`curl` 有回應不算（見 atdd skill「交給使用者看的東西也要先驗收」）。
9. **跟使用者講畫面問題用感受，不用排版術語。** 說「標題又大又粗，像每段都在喊」，不說「35px、字重 900」；數值放在 issue 或程式註解。
7. **閱讀不要被打斷。** 使用者提過名詞連結「會中斷閱讀」。查證、名詞解釋這類「看一下就回來」的東西，盡量留在同一頁（資料來源收合在文末、名詞小卡），不要讓人跳頁。
8. **要求和目標衝突時講出來。** 例如使用者要的效果會讓新手更難讀、或打斷正在做的事，先說明再討論，不要默默照做或默默不做。

## 設計流程

```
使用者提出想法或問題
  ↓ 1. 想清楚：要解決的是什麼閱讀問題？和網站目標（新手讀得懂）衝突嗎？
  ↓ 2. 研究：references/research.md 有沒有答案？沒有就上網查（研究、設計系統、瀏覽器支援度），記下來源和日期
  ↓ 3. 決定：給一個建議（不是選擇題），講清楚為什麼、和使用者原本的想法差在哪
  ↓ 4. 樣稿：方向大 → 2～3 份 HTML 樣稿；小改動 → 實驗分支做一版。用 scripts/shoot.py 截圖、自己先看過
  ↓ 5. 使用者看圖確認
  ↓ 6. 正式做：開 issue（驗收條件）→ 依 atdd skill 先寫測試 → 實作 → 截圖 → PR
  ↓ 7. 記錄：改了設計方向就寫 docs/decisions/；新研究補進 references/research.md
```

步驟 3 的回覆給新手看，用白話，少技術名詞；技術細節放 issue 和程式註解。

## 現在的設計規則

完整內容與理由見 `docs/decisions/0005-site-style-piggy-bank.md`（風格）、`0006-site-layout-route.md`（版面）、`0004-site-design.md`（Tailwind 分工）。重點：

**風格：小豬撲滿（輕鬆版）**
- 使用者要「輕鬆一點」：圓體字（Chiron GoRound TC）、天空藍底、圓角
- **全站只有一個大膽元素**：首頁撲滿（硬幣動畫用真實回測數字）。其他地方保持安靜，不把每個區塊做成卡片、不到處加動畫
- 金幣色只用在「存錢」相關的小地方（站號、引言左線、含息標記）
- 避開常見的 AI 設計套路：米色底＋襯線＋陶土色、全大寫小標、中點分隔、按鈕加箭頭、什麼都做成卡片

**閱讀**
- 內文一行約 38 字（中文橫排不超過 48 字，#52）；只有表格、圖解可以更寬。數字表放不下時自己左右滑；比較表在手機上依項目排（#54）
- 每篇開頭：站號、標題、「重點」1～3 點；標題寫結論，不寫「說明」「介紹」
- 分頁只用在「同一件事的不同面向」，結論不要藏在分頁裡
- 長文章一頁講一件事（`part` 拆頁）；文章依新手路線排序
- 「看一下就回來」的內容留在原頁：資料來源收合、名詞小卡（電腦在名詞旁、手機從底部升起）

**品質底線**（都有自動化測試，改設計後跑 `npm run test:site`）
- 文字對比至少 4.5:1，日間、夜間都要
- 手機寬度不能水平捲動
- 沒有 JavaScript 時內容照樣看得到、連結照樣能點
- 開啟「減少動態效果」時不播動畫
- 鍵盤能操作（Tab、Enter、Esc）

**工具分工**
| 要改什麼 | 改哪裡 |
|---|---|
| 顏色、字體、圓角 | `site/design/tokens.ts`（需要新的顏色就加 token，例如 #50 加了 `shade` 給陰影用） |
| Starlight 頁面細節（表格、引言、側欄） | `site/styles/starlight.css`，只用 `var(--c-*)`／`var(--sl-*)` |
| 元件 | daisyUI ＋ Tailwind utility class；沒有的才自己寫 |
| 文章內容的呈現（自動連結、收合、數字靠右） | `site/plugins/` 的 rehype 外掛，讓 Markdown 原稿保持乾淨 |

## 改完要看整站，不只看改的那一頁

2026-11-04 連續三次「改好了」都不對（#52 邊緣不齊、#54 弄壞名詞小卡、#58 縮欄寬讓電腦表格被擠扁），原因都一樣：只看改到的那一塊。

1. **全站規則測試**：`tests/site/browser/site-wide.test.ts` 對每一頁 × 電腦／手機檢查對齊、名詞連結點得到、表格不用左右滑、格子沒被擠扁。改版面一定要跑
2. **新規則先證明抓得到問題**：在還有問題的版本上跑，確認紅燈、而且列出的就是你看到的問題；誤報要先修掉（例如名詞折成兩行、圓圈標籤），否則測試不可信
3. **逐頁看整頁截圖**：電腦和手機拼在一起看（所有頁），看的是整頁有沒有怪，不是只看改的區塊
4. **畫面改動合併前給使用者看「改前／改後」並排圖**
