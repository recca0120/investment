# 寫第一個驗收測試：用測試設計 API

第一個驗收測試是整個功能中最重要的一步。寫的當下還沒有任何實作，所以只能站在**呼叫者**的角度思考：「我希望怎麼使用這個功能？」這個測試寫完，API 的形狀就決定了。

## 寫之前先回答這幾個問題

| 問題 | 例子（定期定額回測器） |
|---|---|
| 誰會呼叫？ | Streamlit 畫面、之後可能有 CLI 或排程 |
| 呼叫者手上有什麼？ | 代號、每月金額、起訖日期 |
| 呼叫者需要拿回什麼？ | 總投入、期末市值、報酬率、最大跌幅 |
| 需要哪些外部資源？ | 價格資料 → 這就是要用 DI 切開的接縫 |
| 失敗時呼叫者要知道什麼？ | 查不到代號 → 明確的例外，而不是回傳 0 |

## 從測試讀出來的 API 決策

```python
result = run_dca(PRICES, "0050", monthly_amount=1000, start=date(2026, 1, 1), end=date(2026, 3, 31))
assert result.total_invested == 3000
```

這一行測試其實做了好幾個設計決定：

- **依賴當作第一個參數傳入**（`PRICES`）→ use case 不知道資料從哪來，測試可以直接換成 Fake
- **數值參數用 keyword-only**（`monthly_amount=`）→ 呼叫端讀得懂，不會把金額和日期的順序搞混
- **回傳一個有名稱欄位的結果物件**（`result.total_invested`）→ 之後新增欄位（例如年化報酬）不會破壞既有的呼叫者
- **日期用 `date`，不用字串** → 格式轉換是畫面的責任，不是 use case 的責任

寫測試時覺得彆扭，就代表 API 設計不好。這正是在寫實作之前就修正它的時機。

## 選擇第一條驗收條件

從**最主要的成功情境**開始（例如「每月投入、算出總投入與市值」），不要從錯誤處理或邊界情況開始。主要情境決定了 API 的主體，錯誤情境只是在這個主體上補充。

## 寫法

```python
@pytest.mark.criteria("#5-1")
def test_每月投入固定金額_期末計算總投入與市值():
    # Given 0050 三個月價格 100 → 50 → 100，每月投入 1,000 元
    # When 回測 2026-01 ~ 2026-03
    result = run_dca(PRICES, "0050", monthly_amount=1000, start=date(2026, 1, 1), end=date(2026, 3, 31))

    # Then 股數 = 10 + 20 + 10 = 40，總投入 3,000，期末市值 40 × 100 = 4,000
    assert result.total_invested == 3000
    assert result.shares == pytest.approx(40)
    assert result.final_value == pytest.approx(4000)
```

- **名稱**：中文的「情境＋預期結果」
- **資料**：選容易手算的數字（100、50、1,000），讓預期值一眼就能驗算
- **預期值**：在 Then 的註解寫出計算過程
- **斷言**：只斷言這條驗收條件關心的結果，不要順便斷言內部狀態

## 寫完之後

1. 依照測試中的呼叫方式修改骨架：簽名、回傳型別（例如 `DcaResult` dataclass）、`Protocol`
2. 骨架的函式內容維持 `raise NotImplementedError`
3. 執行 `check_red.py "<測試 node id>"`，看到「✅ 正確的紅燈」才開始寫實作

常見的錯誤紅燈與修正方式：

| check_red 的訊息 | 原因 | 修正 |
|---|---|---|
| 測試在收集階段就失敗 | 模組或名稱不存在 | 建立骨架，或修正 import |
| TypeError | 骨架簽名和測試的呼叫方式不同 | 依照測試修改骨架簽名 |
| 測試直接通過 | 斷言沒有驗證到東西，或骨架有預設回傳值 | 檢查斷言，骨架改回 `raise NotImplementedError` |
| 測試還是範本 | 還留著 `pytest.fail("TODO…")` | 寫入真正的測試內容 |
